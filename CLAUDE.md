## Conventions / gotchas

- TypeScript monorepo; four teammates build in parallel against the §4 schema contract. Don't fork table shapes.
- Bryan owns the front-end (`services/web`, complete, deployed at https://fiscus-blue.vercel.app) and is now building backend issue B2.
- Branching: `track/{track}/{issue}-{desc}`; PRs into main need one cross-track review.
- The root .gitignore previously had a Python-template `lib/` rule that silently excluded lib folders — fixed, but if files ever vanish from commits, run `git check-ignore -v <path>`.
- Redaction before Bedrock, always (§5). Card numbers never leave a process unredacted.
- All writes audit via `lib/audit.ts`; embeddings are fixed at 1536 dims (Titan).
- PRD.md files here are Bryan's personal build specs — do not commit them unless asked.

## Learnings

At the end of every session, append one line here: what broke, or what you'd do differently.
- B2 (2026-08-18): Aaron's `lib/redact.ts` was already merged (Luhn-validated); fake card numbers in fixtures must pass the Luhn check or they won't be redacted — use standard test numbers (4111 1111 1111 1111) not invented ones. Also: `npm run` scripts on Windows can't use `node_modules/.bin/tsx` directly — just `tsx` works because npm adds `.bin` to PATH automatically.
- B1/C1/D2 (2026-08-18): PowerShell here-strings (`@'...'@`) can't contain single-quoted apostrophes — git commit messages with contractions ("don't") break the heredoc. Use a temp file for complex PR bodies and `git commit -m "..."` with escaped content for messages. Also: `sessions.pending_documents` JSONB repurposed for Q&A conversation history works but is semantically wrong — future migrations should add a dedicated column rather than repurposing document-queue fields.
- A1 (2026-08-18): the shared dev cluster had zero tables before this session — B1/B2/C1 all developed against mock-db.json fixtures and never actually ran their migrations for real, despite 001-003 already existing in db/migrations/. Don't assume a migration file existing means it's been applied anywhere. Also: this sandboxed session had no Node.js at all (not just missing tsx-on-PATH) and no working cockroach/DB MCP tool despite the issue text claiming one — had to verify the schema by reading `.env`'s COCKROACH_DATABASE_URL directly and hitting the cluster with Python/psycopg2 in a throwaway `.venv` (already gitignored) as a stand-in for the real `pg`-based TS runner. `.env` in this repo uses `KEY = "value"` (spaces + quotes) not plain dotenv `KEY=value` — a naive regex/parser will silently miss it.
- A2 (2026-08-18): an earlier attempt at A2 (`origin/track/a/a2-ingestion-rebase-fix`, never opened as a PR) implemented the whole pipeline in Python via AWS SAM (`services/ingestion-A2/`), with its own `redaction.py` and its own direct `audit_log` INSERT — duplicating `lib/redact.ts` and bypassing `lib/audit.ts` in a second language. Rewrote it as `services/ingestion/s3-extraction/` in TypeScript instead, importing both shared helpers directly. Also: added `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner` to `package.json` but could not run `npm install` (no Node in this sandbox, same as A1/D1) — `package-lock.json` is now out of sync with `package.json`; whoever picks this branch up must run `npm install` before `npm ci` will work in CI.
- D1 (2026-08-18): before writing server-side RBAC, check `services/web/src/lib/rbac.ts` — Bryan's front end already has a real capability matrix and its header says outright the UI copy is decorative and "the real enforcement lives in services/api / D1." Mirror that matrix exactly rather than inventing a different permission model from the issue's prose spec; the two disagreed slightly (issue text implied data_entry has no transaction visibility, the UI matrix grants `view_row_level_transactions` to data_entry) and the deployed UI won. Also: this sandboxed session again had zero Node.js (same as A1's note) — couldn't run `vitest`/`tsc` locally at all, had to review the TS by eye and rely on CI/the user to actually execute `npm test`.
- frontend/real-api-client (2026-08-18): `mcp__claude-in-chrome__resize_window` cannot produce sub-768px CSS viewports on Windows 11 at 1.25 DPR with a maximized Chrome window — the tool reports success but innerWidth stays pinned. Workaround: use JS to constrain the container to target width and screenshot that sub-element. Also: services/api has no HTTP server yet — all API endpoints in `http.ts` are designed from the interface + AGENTS.md schema, not from a running server. The `LeadershipSummary` shape mismatch (CLI outputs prose `SummaryRow`, frontend expects structured numerics) is documented as a known gap in a PR-description comment block at the top of `http.ts`.
- B3 (2026-08-18): despite the issue text presupposing `services/ingestion/embeddings/{client,search}.ts` and `test/search.test.ts` already covered most of B3, this session's checkout had none of the anomaly/template-search pieces and no test/search.test.ts at all — the real gap was (a) `searchTransactions` only ever searched `transactions`, never `templates` (the "which template does this look like?" half of the spec was entirely missing), (b) mock-mode search returned a fake `0.10 + i*0.15` distance instead of any real similarity signal, which would have made anomaly thresholds meaningless, and (c) `transactions.status`'s CHECK constraint didn't allow `review_flagged` (needed migration 006). Also confirmed empirically: `lib/embeddings.ts`'s mock embedder is a pure text-hash, not a semantic embedding — identical strings collapse to L2 distance 0, but otherwise unrelated content all lands in roughly the same ~15-16 distance band regardless of actual semantic closeness in this 1536-dim space, so mock-mode "similarity" only meaningfully distinguishes exact-duplicate extraction text from everything else. That's fine for proving the ranking/anomaly *mechanism* works, but don't read semantic meaning into mock-mode distances. Kept the write-path anomaly test (`checkAndFlagAnomaly`) mocked (`vi.mock` on `client`/`audit`, per the summaries.test.ts pattern) rather than letting it mutate the checked-in fixture, since the checkAndFlagAnomaly writes now; the pure top-k search tests stayed unmocked/read-only against the real fixture, per the issue's suggested pattern.
- C3 (2026-08-19): the real integration point for correction memory turned out to be `services/ingestion/embeddings/src/embed.ts`, not `s3-extraction/src/extract.ts` — the s3-extraction path never computes or persists a transaction embedding at all (a pre-existing gap, not fixed here), so there'd be nothing to run semantic search against; embed.ts already computes the embedding pre-insert and already has a same-shaped post-extraction hook (`checkAndFlagAnomaly`) to mirror. Also confirmed `corrections.field` values are plain strings matching either a top-level transaction column name (`category`, `amount_cents`) or an `extracted_fields[].key` (e.g. `vendor`) — both `db/seed.ts`'s CORRECTIONS fixtures and the front end's `ReviewDetailPage.tsx` treat them identically, so `applyCorrectionMemory` flattens both into one field-name→value map rather than special-casing top-level columns. Confidence threshold: exactly 2 prior corrections agreeing on the identical (field, original_value, corrected_value) triple auto-applies (matches the acceptance criterion's "corrected twice" wording literally); exactly 1 is logged as a suggestion, not applied, so a single one-off correction can't silently become a rule. No new migration was needed — A1's `corrections` table (004) already has every column this required. Root `tsconfig.json` on this branch (merged from B3, not yet from the CI-widening branch) still only covers `lib/**`/`db/**`, so `npm run typecheck` silently skipped `services/ingestion/embeddings/` entirely; ran an ad hoc broader `tsc --noEmit` over that directory by hand and it caught the same `block.type !== 'text'` ContentBlock bug documented in the CI-widening session's notes (fixed here too, in embeddings/src/client.ts's `invokeModel`, since it's on the path this issue touches).
